# Windows 安装体验与客户端更新方案草稿

本文件保留安装与更新方案。0.1.0-beta.1 已将两个安装选项、固定 Beta 身份和可搬迁的构建配方纳入源码，实际构建及普通账户结果见对应 [Beta 记录](releases/0.1.0-beta.1-r1.md)。更新器和签名仍未实施；旧候选及证据保持原样。

## 已确认的需求

- 安装过程中提供“创建桌面快捷方式”复选框，由用户决定。
- 安装完成页提供“立即打开星丛”复选框，由用户决定。
- 客户端发现新版本后，提示版本与说明，由用户选择下载；下载并校验后，再由用户选择重启安装。
- 使用普通账户安装，保留用户的伙伴、聊天、记忆、设置及项目文件。
- 发布者目前考虑中国个人身份，尚无签名证书；最新候选方向是自研客户端源码全开源并评估 MPL-2.0，品牌与官方渠道另行管理。第三方兼容初审仍有待确认项，没有据此正式落许可证或上传代码。

## 当前状态

既有 NSIS 候选关闭了桌面快捷方式和安装完成后启动。客户端“启动时自动检查更新”为禁用占位，没有更新服务、下载逻辑或 `electron-updater` 依赖。

旧候选的安装标识按提交生成，用于保留不同验收包。新 Beta 使用固定 `Asterium.Beta` 和独立默认资料目录，不自动复制或覆盖旧实例资料；后续 Beta 沿用这一身份。旧包不因此获得新选项或更新器。

## 安装选项实现

继续使用当前的 NSIS 引导式安装器。通过自定义 include 在安装目录选择后增加快捷方式选项页，使用完成页的运行复选框。

快捷方式需要真正服从复选框，不仅是将配置改成默认创建。升级时保留已有选择，不在用户取消后于后续更新中擅自补建。创建、重命名和卸载快捷方式只作用于该发布渠道自己的名称和路径。

完成页只有在用户勾选时运行应用；静默升级路径单独处理，不通过复用完成页复选框抢占用户决定。首次安装与之后版本升级均需普通账户验收。

## 签名与 Windows 提示

用户描述的“默认不运行、展开后可继续”提示与 SmartScreen 的未识别应用提示相符，但尚无原始提示截图，因此不能将其认定为某次完整查杀结果。若后续出现防病毒软件具体威胁名称，应另行核查。

未签名应用并非在所有 Windows 环境中都被禁止运行；正式分发应规划可信代码签名。有效签名用于验证发布者与文件完整性，新签名应用仍可能因信誉不足而触发 SmartScreen。自签名与 EV 证书都不提供“立即不再提示”的保证。

微软 Artifact Signing 当前公信个人身份验证仅支持美国或加拿大个人，因此不将该方案直接推荐给中国个人。可进一步核对支持对应个人身份和地区的证书机构或云签名服务的实际申请资格、公开发布者身份与费用；不读取私人证书，不在聊天或仓库保存私钥、密码与签名凭据。

签名流程应覆盖产品应用、安装器和自行提供的 helper，带可信时间戳，并在新候选上验证签名。具体方案选定前，版本说明继续标记“未签名”。

## 更新分发与开源许可

安装包分发、源码许可和品牌使用分别决定。当前候选方向是自研客户端源码全开源、评估 MPL-2.0；官方安装包和更新清单可通过公开仓库的 Releases 或固定 HTTPS 服务分发。未来云端服务与支持可分别设计，不因客户端开源就公开签名私钥、发布凭据或用户资料。

第三方组件继续保留各自许可，不能由根目录 MPL 文件替代。Agent SDK 已从当前源码移除，许可剩余问题以 [跟进清单](licensing/third-party-followup-20261101.md) 为准。标准 MPL 允许合规再分发，“官方发行身份与渠道”不能写成禁止第三方依法发行。在正式许可与上传分别确认前，不将发布副本推为公共仓库。

公开客户端不能内置维护者的私人 GitHub Token。发布凭据仅用于受控的构建发布环境；普通客户端读取不需要这些凭据的公开更新端点。具体仓库归属、地址及 stable / preview 渠道仍待确定。

## 拟议更新链路

1. 在主进程接入与锁定工具链匹配的 `electron-updater`，由固定 IPC 提供“检查更新、下载、稍后安装、重启安装”操作；只接受已配置更新源，开发或未配置状态明确显示不可用。
2. 设置页显示当前版本、检查状态、新版本说明、下载进度和失败原因。可另提供启动时检查选项，但发现更新不自动下载、不自动安装。
3. 显式关闭自动下载与退出时自动安装。安装前再次确认，正在执行的伙伴任务、文件操作或自动化未安全结束时不强制重启。
4. 从可信更新源获取版本清单；下载后核对清单校验值与发布者签名，不把跳过校验作为正式渠道的默认实现。
5. 更新替换应用程序文件，保留用户数据和外部项目。涉及数据结构变化时，单独设计版本迁移、备份、失败处理及降级限制，不能只验证程序可以启动。
6. 开发机先模拟检查状态、取消、网络失败、校验失败与任务阻塞，再用两个明确版本做真实安装升级验收，核对资料与快捷方式选择是否保留。

发布时生成新版本安装包及 `latest.yml` 等更新元数据；具体渠道名称应与客户端配置一致，可选差分文件按冻结配置产生。只有用户授权发布后，才上传对应渠道的文件与清单。

当前已安装的候选没有更新器。首次迁移到支持更新的客户端需要手动安装一次，之后才可能使用客户端更新；不声称当前旧包能自行获得尚不存在的更新逻辑。

## 后续实施顺序

1. 关闭第三方许可待确认项，确定 MPL 适用的自研文件边界、品牌政策、更新渠道和固定发布身份。
2. 将可复核的安装器配方纳入明确版本管理，完成两个安装选项，保留旧候选。
3. 实现更新状态与主进程链路，补充测试及能力条目；新增代码未提交前不写未来 SHA 或伪造核验绑定。
4. 配置选定签名方式，完成新候选的来源、哈希、签名、安装和跨版本数据保留验收。
5. 单独确认上传和发布操作；不因本方案存在而自动创建远端、提交或 push。
