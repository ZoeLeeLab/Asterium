# 委派任务权限

## 目标与实现边界

任务由发起伙伴按用户的实际要求选择 `access: read | write`。省略时按只读处理，不根据“部署”等关键词推断授权。只读任务可以查询、评审和提出方案；执行任务只能在用户授权范围与原会话权限内修改或运行操作。附件不能自行扩大授权，用户可以明确要求按附件完成任务。

本轮从远端 main `f633acdc2d06d03d8553d722ce58d77dd43d2d9d` 创建独立分支和工作树。委派回传分支中的待提交修改与既有验收包保持原状。本轮不改界面，不修改其他拆分工作树，不部署外部宿主。

## 数据流与职责

1. `PartnerDelegation.ts` 校验任务的 access 并持久保存；旧任务没有字段时按 read 解释。
2. Main 从真实发起命令获取原会话权限，拒绝只读或 Plan 发起 write；模型不能传入父会话权限。
3. `DelegationAccess.ts` 负责权限判断、宿主能力协商与提示词，不在 IPC 中堆叠业务规则。
4. 接回伙伴先查询已认证宿主的能力。v1 只支持原有 Markdown 只读复核。v2 明确声明 read/write 并在请求、回执中绑定有效权限；write 不降级成 v1 复核。
5. 排队执行前再次校验当前来源会话与目标宿主，权限被收紧时不执行超出范围的任务。丢失回执只查询原 ID，不重发执行。
6. 普通本地/API 一次性委派目前仍只读、无执行工具；名单如实声明只支持 read，write 返回明确不支持。

## 外部宿主 v2 契约

沿用 `/api/asterium/reviews` 的认证、文件上传、请求 ID、线程绑定、去重与查询流程。

- 能力：`{ version: 2, threadId: "synthetic-thread", accessModes: ["read", "write"] }`。
- 请求：保留 v1 的 requestId/threadId/message/file；version 为 2，并携带 `execution: { access: "write", permissionMode: "manual" }`。read 必须携带 read_only；write 允许 manual/automatic/full，不能超出父会话。
- 回执：回显 version、requestId、threadId 和完整 execution。不得把 v2 回执降级为 v1，也不能用不匹配的权限回执确认成功。
- 宿主应在启动前取请求权限与接收线程实际权限的共同允许范围。read 在工具执行层禁止修改；write 保留原有审批与目标范围。需要人工确认而后台无法提供时，返回 `approval_required`；权限不足返回 `permission_denied`，均不启动需越权的操作。
- 权限属于载荷指纹的一部分；同 ID 改权限必须拒绝。宿主升级后仍支持 v1 只读请求及旧任务查询。

星丛客户端支持不代表外部宿主已经接线，实际读写和部署必须用明确指定的合成测试连接另行验收。不能仅凭提示词宣称强制只读或服务器部署已生效。

v1 是历史复核约定，只有提示词和既有宿主策略，没有 v2 的结构化权限回显；不把它描述成已验收的工具级强制只读。Codex 新线程会注册新增的 access 参数；既有原生线程仍使用创建时的工具清单，本轮不迁移或重建原线程。旧清单不能因此被宣称已支持选择 write，需在后续原生工具升级中单独处理。
